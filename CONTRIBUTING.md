# Contributing

Read `docs/SETUP.md`, `docs/EXTRACTION.md`, `docs/ARCHITECTURE.md` and `docs/COMPLETION.md`. Domain/display name: **HomePod Sensor Link** / `homepod_sensor_link`. Repository and local folder: `ha-homepod-sensor-link`. The project uses GPL-3.0; see `LICENSE`.

The final design owns new sensor entities, adopts existing native entries without mutation, defaults recovery on per device, permits local/admin HTTP input without an acknowledgement, and automatically deletes owned credentials/history on removal. Do not reintroduce a legacy compatibility package, storage migration or retained-data purge flow. Preserve conflict detection and native measurement identities/history.

Run `sh scripts/validate.sh`. The HA 2026.10.0/2026.11.0 matrix is deliberate; containers are offline and use generated identities. Keep real aiohomekit connector cleanup regressions, rolling attempt/reload limits, cancellation, persist-before-write, exact identifier spelling, source/admin pins and actual sensor-publication tests. Test the HTTP security boundary before body reads, partial setup, restart/Resume, deletion races, and source-key disposal.

Read the [development guide](docs/DEVELOPMENT.md) for pinned tooling, coverage reports and focused commands. Keep Python Ruff-formatted and correctness-lint clean. Add meaningful behavioural tests with each change. Keep every integration module at exactly 100% statements and branches, with no exclusions; the credential panel also has exact Node coverage gates. Strict mypy and upstream hassfest must pass. Do not add tolerated misses, suppressions or omit modules to satisfy a gate. The [quality target](docs/QUALITY.md) keeps external requirements explicit.

Maintain action metadata in `services.yaml`, `strings.json` and the English translation together. Update the [changelog](CHANGELOG.md), edit canonical documentation, and regenerate the [local wiki](wiki/Home.md) with `python3 scripts/build_wiki.py`. Local links, generated-page drift and community automation contracts are checked by validation. Use the prepared issue/PR forms with sanitised evidence only.

Do not access live systems, 1Password, real backups/keychains or credentials during ordinary development. Separately authorised live work must follow the existing 1Password workflow. Do not weaken OS protections, network verification, permissions or approval settings. Never add secrets/household data to fixtures, issue text or logs.

`python3 scripts/check_public_content.py --history --require-git` audits files, staged content and reachable history. Missing metadata is fatal in strict mode; temporary synthetic Git fixtures test the scanner but do not authenticate this project’s initial commit. Review staged diffs/file lists as well as scanner output.

`python3 scripts/package.py --output /tmp/homepod-sensor-link-local.zip` creates a deterministic local single-component archive and SHA-256 sidecar after scanning its exact bytes. CI keeps `GITHUB_TOKEN` at `contents: read`; validation is secret-free and cannot deploy or publish releases. A separate Codecov job uploads only the two validated Python coverage XML files on trusted `main` runs using `CODECOV_TOKEN`. Pull-request runs never receive that token through this workflow. Local tests, hosted CI, reporting, publication, installation and real-device verification are separate outcomes. Public development issues use the repository's issue forms; private security reporting and HACS acceptance remain outstanding.
