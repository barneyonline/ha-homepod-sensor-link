# HomePod Sensor Link UI and removal API research

This file records API facts and earlier implementation options. The final policy and implemented lifecycle are in `ARCHITECTURE.md`: recovery defaults on, HTTP has no acknowledgement, cleanup is automatic, and no compatibility transition is retained.

Checked against Home Assistant Core tags `2026.10.0` and `2026.11.0` on 2026-11-07. This is source research; no live Home Assistant access or device writes occurred. The target domain is only `homepod_sensor_link`.

## Credential import

`ConfigFlowContext` does not carry an HTTP request or authenticated user. The generic flow HTTP views call `async_init(..., context=self.get_context(data))` and `async_configure(flow_id, data)`; the initial generic context is empty. Core config-entry views add the source/entry ID and apply administrator checks. Do not accept an administrator flag or client-supplied user ID as proof. [Generic flow views](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/data_entry_flow.py#L58-L120), [config-entry HTTP views](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/config/config_entries.py#L150-L230).

There is an actual request context: `homeassistant.components.http.current_request` is exported in both supported tags. It is a `ContextVar[Request | None]`, defaulting to `None`, populated by HTTP middleware. `HomeAssistantView.requires_auth` defaults to `True`; authentication enforcement reads `ha_authenticated`. `request["hass_user"]` supplies the actual user; `@require_admin` checks `user.is_admin`. [2026.10 HTTP exports](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/http/__init__.py#L14-L20), [2026.11 HTTP exports](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/http/__init__.py#L103-L119), [request/context/authentication implementation](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/http.py#L31-L38), [middleware](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/http/request_context.py#L11-L24), [admin decorator](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/http/decorators.py#L57-L83).

The standard `FileSelector(FileSelectorConfig(accept=...))` validates a string UUID; its configuration exposes only `accept`, with no integration-specific destination or security gate. [Selector source](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/selector.py#L1104-L1132).

The generic `/api/file_upload` view accepts authenticated multipart uploads, uses a 100 MiB limit and a shared file-ID map, and records no uploader/user ID. It has no administrator or local-network check. The executor-only `process_uploaded_file(hass, file_id)` context manager yields a path and deletes the upload at context exit. The temporary root is mode `0700`; unused files are removed on shutdown or the next initialization, rather than by an individual short expiry. The implementation is present in both target tags. **Inference:** gating only the subsequent flow submission cannot enforce local/admin restrictions on the earlier secret upload itself. [2026.11 implementation](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/file_upload/__init__.py), [2026.10 implementation](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/file_upload/__init__.py).

### Minimal proposed implementation

Use a small custom panel with a normal file input and a dedicated authenticated multipart upload view. This is a project design recommendation, not a Core credential-import service:

1. Register a secret-free JS module and `await panel_custom.async_register_panel(hass, frontend_url_path="homepod-sensor-link-import", webcomponent_name="homepod-sensor-link-import", module_url=..., require_admin=True, config_panel_domain=DOMAIN)`. The panel API exists with the same relevant signature in both tags. A panel element receives `hass`; its API exposes `fetchWithAuth(path: string, init?: Record<string, any>): Promise<Response>`. Call that with a `FormData` body to the dedicated endpoint. Panel visibility is not the server-side authorization boundary. Ensure registration occurs before first configuration, rather than only after an entry exists. [2026.11 panel API](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/panel_custom/__init__.py#L75-L137), [2026.10 panel API](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/panel_custom/__init__.py#L75-L137), [frontend types bundled by Core 2026.11](https://github.com/home-assistant/frontend/blob/20261028.4/src/types.ts#L239-L264), [panel element type](https://github.com/home-assistant/frontend/blob/20261028.4/src/types.ts#L334-L339).
2. Register `HomeAssistantView` with `requires_auth = True` and an `@require_admin` `async def post(self, request: web.Request) -> web.Response`. Before reading any body bytes, reject Cloud connections and missing/malformed/non-local `request.remote`. Use `is_cloud_connection(hass)` and `is_local(ip_address(request.remote))`. HA's local predicate includes loopback, RFC1918, IPv6 unique-local and link-local ranges. HTTP is allowed; no TLS-only condition or extra acknowledgement is necessary. [Local predicate](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/util/network.py#L7-L48), [Cloud helper](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/network.py#L344-L349).
3. Trust the `request.remote` already resolved by Core's trusted-proxy middleware, not caller-supplied forwarding headers. Explicitly reject Cloud because the middleware bypasses normal forwarding handling for Cloud requests. `is_internal_request(hass)` matches configured/internal request URL/Host and is insufficient as source-network proof. Proper proxy configuration remains necessary: a private proxy that discards client identity cannot establish a remote client's true network. [Forwarded middleware](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/http/forwarded.py#L65-L129), [URL helper implementation](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/network.py#L249-L280).
4. Enforce an independent small streaming byte cap and timeout, validate CSV/JSON without echoing file names, values or parser exceptions, and keep parsed credentials in memory. Do not use Core 2026.11's new `HomeAssistantView.max_body_size` as the only limiter: it is absent from 2026.10. Bound reads explicitly. [2026.10 base view](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/helpers/http.py#L115-L129), [2026.11 base view](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/http.py#L119-L127).
5. Return an unpredictable, short-lived, one-use token whose in-memory record binds parsed credentials to the authenticated user ID and intended flow ID. The flow must obtain `current_request.get()` and repeat authentication, administrator, Cloud/network and same-user checks before consuming it. Never put credentials in flow context, schema defaults, descriptions, results, logs, URLs, options or diagnostic objects. Reject absent request contexts for credential operations. Purge tokens on expiry, abort, successful consumption and shutdown. A token alone is not authorization.
6. Standard flow can present a link to the panel or use `async_external_step(*, step_id=..., url=...)` and `async_external_step_done(*, next_step_id=...)`. A same-origin URL needs only the nonsecret flow ID. The authenticated panel may submit the import token back through the ordinary flow endpoint; both endpoints enforce ownership. [External step API](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/data_entry_flow.py#L763-L792).

Only persist the selected, validated operational credential record in an integration-owned private store after successful onboarding. Drop imported recovery/admin records as soon as unnecessary. Pending uploads should never become durable flow data.

## One integration entry, per-device removal

Both target versions support `hass.config_entries.async_add_subentry(entry, ConfigSubentry(...))`, `async_remove_subentry(entry, subentry_id) -> bool`, and `async_update_subentry(entry, subentry, *, data=..., title=..., unique_id=...) -> bool`. These are loop-thread callbacks, not awaitables. Subentry removal clears associated device/entity registry records and notifies entry update listeners. Core exposes an admin-only `config_entries/subentries/delete` WebSocket command that calls removal directly. There is no integration-specific pre-removal callback in that path. `ConfigFlow.async_get_supported_subentry_types(cls, config_entry)` returns a mapping of types to `ConfigSubentryFlow` classes. [2026.10 subentries](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/config_entries.py#L2601-L2668), [2026.11 subentries](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/config_entries.py#L2677-L2739), [delete command](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/config/config_entries.py#L786-L812).

The device-delete contract is `async def async_remove_config_entry_device(hass, config_entry, device_entry) -> bool`. The admin command calls it and requires a truthy result before removing the registry device. Integration-entry deletion invokes `async def async_remove_entry(hass, entry) -> None`. [2026.10 device removal](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/config/device_registry.py#L197-L268), [2026.11 device removal](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/config/device_registry.py#L200-L274), [entry removal callback](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/config_entries.py#L1131-L1167).

Proposed lifecycle:

- Prefer one owned device record per newly onboarded HomePod, with public metadata and an opaque credential-store key; persist private credentials separately. Either plain entry-owned device metadata or subentries are viable. Plain metadata avoids subentry deletion's lack of an awaited credential-cleanup hook.
- If using subentries, register a persistent entry update listener that diffs stored device keys against remaining subentries and awaits private-store deletion before restarting any workers. Perform the same reconciliation before starting workers on setup, covering deletion while unloaded or interruption during cleanup. Keep cleanup independently accessible from the runtime coordinator. Every removal route must reach the same idempotent purge routine.
- The device-removal hook first verifies ownership, stops and awaits that device's work, removes its private credentials/state, then removes its public metadata/subentry and returns `True`. Return `False` on unknown/unowned devices. Never delete or update a `homekit_controller` entry/entity/device when removing an adopted reference.
- The integration-removal hook stops outstanding work if necessary and deletes all integration-owned credential/state stores and pending tokens, including when no runtime coordinator is loaded. Unloading/reloading alone must preserve durable credentials.
- Adopted native sensors remain references to native entities. Newly onboarded sensors are owned by this integration. Removing a reference or integration performs no HomeKit pairing operation and no native-entry mutation.

No Docker verification was attempted in this research task. Tagged-source checks establish available contracts; local/offline integration tests should still exercise real HA HTTP authentication, request context, upload size handling, per-device removal and entry removal before claiming end-to-end support.
