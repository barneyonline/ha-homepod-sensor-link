# Home Assistant 2026.12 beta compatibility

HomePod Sensor Link 1.3.1 at `e7b2e156272a` passed the synthetic compatibility suite and loopback smoke tests on the official Home Assistant Core `2026.12.0b2` image. The review found no release blocker. The beta exposed a Repairs warning in a test fixture that creates multiple config entries on the same synthetic Home Assistant instance. A normal Home Assistant remove-and-readd probe cleared the old Repairs and produced no usage warning.

Reviewed on 28 November 2026. Core `2026.12.0b2` (`78677c0`, published 26 November UTC) was the latest published 2026.12 tag. [Core beta release](https://github.com/home-assistant/core/releases/tag/2026.12.0b2) · [Core beta release notes entry point](https://github.com/home-assistant/core/releases/tag/2026.12.0b0) · [Home Assistant Contributors blog](https://contributors.home-assistant.io/blog/)

## Core changes relevant to HomePod Sensor Link

- **Config flow results.** Core now requires the `FlowResultType` enum for a step result's `type`. The integration's onboarding, reconfigure and reauthentication paths use the Home Assistant flow helpers, which supply the enum. The forms, menus and progress calls also supply explicit step IDs ahead of the separate 2027.5 requirement. The October lifecycle change continues to accept Boolean setup, unload and migration returns from custom integrations. [Config flow implementation](../../custom_components/homepod_sensor_link/config_flow.py) · [Core #189583](https://github.com/home-assistant/core/pull/189583) · [Step IDs](https://contributors.home-assistant.io/blog/2026/10/23/flow-results-require-step-id/) · [Lifecycle returns](https://contributors.home-assistant.io/blog/2026/10/23/config-entry-methods-return-none/)
- **Config entry reloads.** The May notice originally announced an error when a flow schedules a reload for an entry with an update listener. The merged change raises for built-in integrations and logs a warning while still reloading custom integrations. HomePod Sensor Link calls `async_update_reload_and_abort()` without attaching a config entry update listener. [May notice](https://contributors.home-assistant.io/blog/2026/05/07/config-entry-listener-together-with-reloading-methods/) · [Core #189565](https://github.com/home-assistant/core/pull/189565)
- **Device info.** The beta deprecates dict-style `DeviceInfo` and `ChildDeviceInfo` access and old device info constants until their removal in 2027.12. It also enforces string values for fields including `manufacturer` and `model`. The integration constructs `DeviceInfo` through keyword arguments and supplies string literals for those fields. Its `DeviceInfo(**{…})` expression unpacks a plain keyword argument dict. The Bluetooth dict deprecation is specific to Bluetooth processor coordinators. The registry cleanup uses `async_entries_for_config_entry` and registry attributes instead of the older `DeviceEntry.config_entries` properties due to be removed in 2027.10. [Entity implementation](../../custom_components/homepod_sensor_link/entity.py) · [Dict-style access](https://contributors.home-assistant.io/blog/2026/11/19/device-info-mapping/) · [Deprecated constants](https://contributors.home-assistant.io/blog/2026/11/10/device-info-constants/) · [Core #190077](https://github.com/home-assistant/core/pull/190077) · [Bluetooth data updates](https://contributors.home-assistant.io/blog/2026/11/10/bluetooth-plain-device-info/) · [Device registry properties](https://contributors.home-assistant.io/blog/2026/09/15/device-entry-config-entries-deprecation/)
- **Coordinator and repairs.** The new `UpdateFailedUnreachable` exception is an optional `UpdateFailed` subclass that logs coordinator reachability failures at info level. This integration reports reachability for each HomePod and uses `UpdateFailed` when the overall checks fail. Repairs already link issues to their config entry. The beta adds optional subentry association. [Coordinator implementation](../../custom_components/homepod_sensor_link/coordinator.py) · [Repair implementation](../../custom_components/homepod_sensor_link/repairs.py) · [Coordinator exception](https://contributors.home-assistant.io/blog/2026/11/13/update-failed-unreachable/) · [Repair association](https://contributors.home-assistant.io/blog/2026/10/28/issue-registry-refresh/)
- **Discovery dependencies.** Core's zeroconf requirement moves from `0.152.0` at the supported 2026.11.0 floor to `0.154.0` in the beta. The library diff touches DNS record and incoming packet internals used by the directed discovery code, which makes the synthetic unicast request and parser tests pertinent. Core's HomeKit Device manifest continues to pin `aiohomekit==4.0.1`, which satisfies the integration's `aiohomekit>=4.0.1` requirement. Both Core versions require Python `>=3.14.2`. [Directed discovery](../../custom_components/homepod_sensor_link/directed_discovery.py) · [Zeroconf version comparison](https://github.com/python-zeroconf/python-zeroconf/compare/0.152.0...0.154.0) · [Core 2026.11 zeroconf pin](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/components/zeroconf/manifest.json) · [Beta zeroconf pin](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/components/zeroconf/manifest.json) · [Beta HomeKit Device pin](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/components/homekit_controller/manifest.json) · [Core 2026.11 Python requirement](https://github.com/home-assistant/core/blob/2026.11.0/pyproject.toml) · [Beta Python requirement](https://github.com/home-assistant/core/blob/2026.12.0b2/pyproject.toml)
- **Built-in HomeKit Device.** Its new child-device mapping applies to accessories with repeated outlets or lights. HomePod Sensor Link declares `zeroconf` and `http` as its HA dependencies, owns its own aiohomekit controller, and publishes its own temperature, humidity and diagnostic sensors. [Manifest](../../custom_components/homepod_sensor_link/manifest.json) · [HomeKit Device change](https://github.com/home-assistant/core/pull/191607)

Both runs used `aiohomekit 4.0.1`, the repository coverage runner, a read-only checkout and Docker's `none` network. After removing unused Docker images, the beta suite was rerun on `linux/arm64` using the official tag, whose multi-platform image index has digest prefix `7b02599ebb74`. This confirmed the earlier wheel-based result. The tested image contains Python `3.14.10`, frontend `20261125.1`, and coverage `7.17.5`. The beta run recorded zero unhandled background-task errors. Native sensor registration, config-flow interactions and directed DNS-SD packet handling were exercised with synthetic inputs. [Official container images](https://github.com/home-assistant/core/pkgs/container/home-assistant) · [Repository runner](../../scripts/run_tests.py) · [Packet tests](../../tests/test_unicast_discovery.py)

Additional smoke tests passed on the official image:

- **Directed discovery.** Real HAP and AirPlay DNS-SD exchanges over IPv4 and IPv6 loopback used ephemeral reply ports and sent no known answers. The discovery code ignored malformed replies and returned the port and address from a valid response.
- **Native credential forms.** A disposable Home Assistant instance answered real loopback HTTP requests with synthetic discovery results. Unauthenticated and non-admin requests were rejected. A local administrator reached the export and manual forms. Home Assistant serialized the multiline export field and the password selector. Invalid submissions returned validation errors and omitted the submitted values.
- **Browser onboarding.** Host-side headless Chromium connected to a disposable official-image container over loopback. With synthetic discovery results, it used the beta integration picker and reached device selection, recovery policy and both credential forms. The export and manual forms were checked in separate attempts, showing a multiline export field and a masked manual private-key field.

A separate LAN check used Zeroconf `0.154.0` and the integration's directed DNS-SD implementation. Real HomePods returned matching identities, addresses and HAP ports over multicast and directed IPv4 queries. This confirms endpoint discovery. The stable `2026.12.0` release was still pending on the review date. Authenticated sensor publication on the live Home Assistant remains unverified.

The original preflight sample test created a new config entry in each subtest while keeping the same device key and Repairs registry. Core 2026.12 now warns when an existing issue ID is recreated under a different config entry. The test's incomplete Home Assistant bootstrap made the warning call raise `Frame helper not set up`, which the coordinator logged while the test still passed. With Core's setup helpers enabled, the same fixture produced two usage warnings. A separate probe created two Repairs on a loaded entry, removed it through Core, and re-added a replacement. Both Repairs were cleared by removal and were successfully registered to the replacement without a usage warning. [Preflight fixture](../../tests/test_startup_performance.py#L935) · [Core issue registry](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/helpers/issue_registry.py#L341-L355) · [Core config entry cleanup](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/config_entries.py#L2439-L2449)

The fixture now uses an active device with recovery disabled so provisioning and recovery cannot account for the read. Each case checks that the refresh reads exactly once, records the new measurements and reaches the expected device status. Then it clears the entry, its Repairs and persisted device state. The repository validation matrix and coverage upload now include `2026.12.0b2` alongside the `2026.11.0` minimum. Both exact coverage gates passed again after the fixture change. Repository contracts, automation, quality evidence, Ruff and hassfest also passed. Colima ran out of memory during the bundled validation, so the pinned mypy `2.3.1` check ran on macOS with the 2026.11.0 package and Linux type-checking platform. ## Improvement priorities

1. **Replace the beta pin when stable 2026.12 is published.** Keep the 2026.11.0 minimum as a separate check. Pin the coverage version shipped in the stable image. Repeat the smoke checks on stable and verify authenticated temperature and humidity publication with a real HomePod. [Validation matrix](../../devtools/validation.json)
2. **Reduce dependency on Zeroconf packet internals.** Compare the documented APIs against the existing directed discovery requirements. Any replacement must preserve the temporary unicast socket, fresh replies, no known answers in the query, and isolation from Core's shared discovery cache. The current packet path passed on `0.154.0`. [Directed discovery](../../custom_components/homepod_sensor_link/directed_discovery.py) · [Zeroconf public API](https://python-zeroconf.readthedocs.io/en/latest/api.html)
3. **Improve Marketplace metadata and presentation.** The manifest can declare the `sensors.temperature_humidity` category. The README already marks the numbered installation block for exclusion. The header's install badge and Install link still appear, and the exclusion block also hides the initial credential-preparation step. Consider hiding the duplicate install prompts and surfacing the credential guide in the Marketplace rendering. [Manifest](../../custom_components/homepod_sensor_link/manifest.json) · [README](../../README.md#L7) · [Sensor categories](https://contributors.home-assistant.io/core/integrations/categories/#sensors) · [Marketplace README markers](https://contributors.home-assistant.io/blog/2026/11/25/leave-readme-sections-out-of-the-marketplace/)

`UpdateFailedUnreachable` is a lower-priority logging option for a positively identified coordinator-wide transport outage. The current design records ordinary reachability per HomePod. A blanket switch from `UpdateFailed` would also lower the severity of unexpected inventory, storage and publication failures and would need a compatibility path for the current 2026.11.0 minimum.
