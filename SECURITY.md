# Security and private data

Controller administrator identities can authorise pairing changes. HomePod Sensor Link defaults recovery **on**, per device, and retains the verified administrator credential while that feature needs it.

- Extraction is explicit and user-authorised. A setup code/QR is not an existing controller identity. The integration never extracts a keychain, accesses a backup, disables SIP/AMFI, bypasses certificate/host-key checks or edits native HA credential storage.
- Normal input uses standard Home Assistant config-flow forms, with a choice of pasting CSV/JSON or entering controller credentials. Cloud/non-local/unauthenticated/non-admin and users other than the administrator who started the flow are rejected. HTTP is allowed without an acknowledgement checkbox; it carries the credential payload without transport encryption. Trust HA’s resolved peer only, and configure proxies to preserve client identity. A proxy that hides remote clients defeats any application source-IP distinction.
- Select only required HAP records. Never submit a full backup, unrelated password groups or incomplete/binary placeholder values. Raw exports are bounded memory only, not schema defaults, core config data, generic file-upload storage, logs, URLs or diagnostics. The private-key field is masked; pasted exports are visible while being edited. Validation failures return empty forms without echoing submitted credentials. Cancelling setup discards the parsed import.
- Private operational data is kept in `.storage/homepod_sensor_link/data.json`: directory 0700, file 0600, process ownership and no-follow reads. Writes are atomic and drained across cancellation. Source/admin pins and dedicated controller identities are verified; an identity/key/permission change fails closed.
- New devices receive regular User controller permissions; the implementation exposes sensor reads. User permission is not an accessory-enforced “temperature-only” capability. Existing native controller permissions are not changed. The supplied administrator is used for verified add-only provisioning/recovery.
- Recovery restores only the missing pinned HA row, preserves every pre-existing row and verifies fresh authentication plus actual sensor reports. Network/discovery, cleanup-only and failed onboarding matching never authorise recovery writes. Failure evidence, rolling repair/reload counters and blocked states persist across normal restart; every restart begins a fresh ten-minute startup grace. Pairing checkpoints always perform durable writes, even when their in-memory values are unchanged.
- Removing a device automatically deletes its owned credentials and recovery history. Removing the integration deletes all owned credentials, pending imports/journals and history. Neither action revokes on-device pairings, deletes native sensor entries/history, erases external backups/exports or guarantees forensic erasure. Removal/re-add intentionally resets cooldown history; a normal restart does not.
- No legacy wrapper or migration is included. The integration neither reads nor deletes `homepod_recovery` storage. Competing recovery engines are blocked rather than run concurrently.
- Never commit real private/public controller keys, pairing bundles, accessory/controller IDs, native entry IDs, live addresses, household mappings, logs, diagnostics, exports or HA storage. Use generated disposable identities and documentation-only endpoints in tests. Curated diagnostics use anonymous ordinals and controlled status/error metadata; they omit raw exception messages, payloads, names, addresses and sensitive locals.

The optional macOS extraction procedure temporarily disables SIP/AMFI. The user-run `scripts/macos_homekit_wizard.sh` builds our bundled Swift helper against Apple frameworks before security changes, saves original boot arguments, and signs/runs the helper only after explicit confirmation. No third-party packages are downloaded. The helper queries only generic-password items in `com.apple.hap.pairing`, explicitly using the data-protection keychain so access-group filtering applies. Its signing entitlements contain only that group. It implements no keychain writes or legacy-keychain fallback, validates controller key pairs before rendering, and refuses credential output to a terminal, pipe, shared or hard-linked file. Its harmless help/query-description modes never access a keychain.

The wizard stores the dump and selected JSON in an owner-only folder outside the repository and blocks JSON export until SIP, the original NVRAM value and the running kernel's boot arguments pass restoration checks. It then reads the private dump automatically, rejects incomplete or conflicting records, and lists only identifiers for numbered selection. Keys are never printed or requested as terminal input. A sole record is selected automatically; multiple records require an explicit selection, bounded to three controller identities and 64 accessories. Only selected credentials enter the generated 0600 JSON file. After saving, syncing and reading back the JSON, the wizard records its filename and both file digests before removing the temporary dump. Failed writes or verification retain the dump; interrupted cleanup can resume using the recorded JSON without copying keys again. Changed files, links or unsafe permissions block cleanup. Signing certificates and original HomeKit keychain records are not deleted. After HA setup succeeds, delete the JSON or move it to secure encrypted storage, and clear copied credentials from the clipboard.

State files are data, never sourced shell code. The wizard prints recovery instructions on interrupted or failed runs. SIP/AMFI changes, NVRAM writes, privileged commands and restarts remain manual; the wizard never executes them. Keep its output private and restore protections immediately after extraction, including after a failure. Do not run the wizard against a real keychain during ordinary development or tests. Native synthetic tests compile a separate entry point with real keychain access excluded and exercise conversion of an actual synthetic Swift dump. Live access by a developer still needs separate authorisation and the existing 1Password workflow.

Use GitHub issues for general support. For security concerns, request a private reporting channel before sharing details. Never post vulnerability details, credentials or complete HA storage/diagnostics in public issues.
